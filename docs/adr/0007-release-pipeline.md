# 0007 — A tag publishes the package with the built window inside; the marketplace entry installs that package

## Status

Accepted, 2026-11-03. RMA-126, RMA-177. Closes the open point of [0001](0001-vue-window-with-a-build.md): who builds `dist/` for a user. Amended 2026-11-03, RMA-217: the plugin left this repository, RMA-231: an install updates itself, 2026-11-04, RMA-329: only on the user's click or yes, RMA-330: not when pinned, and RMA-341: the Claude plugin updates with it; see the amendments under Decision.

## Context

The window needs a build (0001) and the repository keeps sources only, `dist/` is gitignored. A Claude Code marketplace entry with a git source copies the repository as it is, so a user who installs from git gets a server without a window, and AGENTS.md says the user never builds. The maintainer decided on 2026-11-03 that the marketplace is BladeForge, not a marketplace of this repository's own, and that there is no submodule: the entry points at a published package.

## Decision

A tag `vX.Y.Z` on `main` runs `.github/workflows/release.yml`: it checks that the tag, `package.json` and `.claude-plugin/plugin.json` carry the same version, runs `npm run check`, builds `dist/`, packs, publishes the `whose-turn` package to npm under the maintainer's account with provenance (under `latest` on every publish, prereleases included, plus the channel tag such as `alpha` for a prerelease; RMA-230, so that every install, which follows `latest`, gets each alpha), and attaches the same tarball to a GitHub Release. The package carries only what the installed plugin runs: the server, the connectors, the plugin files (`bin/`, `hooks/`, `commands/`, `skills/`, `.claude-plugin/plugin.json`), `dist/`, the two shell scripts, the example config and the changelog; `test/package.test.mjs` pins that list. The BladeForge marketplace lists `whose-turn` with an `npm` source (`package: "whose-turn"`, `version: "alpha"` during the alpha, `latest` after), so `claude plugin install whose-turn@bladeforge` fetches the published package; Claude Code unpacks it without running scripts and installs no dependencies, because the package has none at runtime. The repository's own `.claude-plugin/marketplace.json` is gone; a checkout is loaded for development with `claude --plugin-dir`.

**Amendment, 2026-11-03 (RMA-217).** The package is the server and the window only: `server.mjs`, `lib/`, `connectors/`, `dist/`, `install.sh`, `open.sh`, the example config and the changelog. The plugin (skill, command, hooks, MCP server, its scripts and `plugin.json`) lives in BladeForge as `plugins/whose-turn`, a relative-path entry of that marketplace rather than an `npm` source; it installs this package into its data directory and starts `server.mjs` from there, and calls `install.sh` and `open.sh` from the same path. The release workflow checks the tag against `package.json` alone. Why: the maintainer's rule is that dashboard code lives here and skills live in BladeForge, one release pipeline per repository; a plugin inside the package tied every skill text change to an npm release of the server, and BladeForge's own checks never saw the skill.

**Amendment, 2026-11-03 (RMA-239, RMA-240).** The `release` branch releases, not `main` and not a pushed tag. `main` collects changes; moving `release` to `main` is the decision to ship. `release.yml` runs on a push to `release` (or by hand), reads the version, stops when `v<version>` already exists, and otherwise publishes and then creates the tag and the GitHub Release itself. Why: the maintainer wants many changes in `main` without a rebuild and a publish for each, and a release to need no tag from him, and a tag is one more step a person or an agent has to take, which the agent's permissions refuse.

**Amendment, 2026-11-03 (RMA-231).** An installed package updates itself. The server checks the npm dist-tags every ten minutes (`UPDATE_CHECK_MS` in `lib/update.mjs`), through the ETag cache of `lib/http-client.mjs` so an unchanged answer costs a 304; it follows the `latest` dist-tag, which `release.yml` moves on every publish, prereleases included (RMA-230), because the maintainer wants every install on the newest version, reports the result as `update` in `/api/summary`, `/api/state` and the stream, and raises one desktop notification per version. `POST /api/update` installs that version with `npm install --prefix <data>/app` into the place the plugin installed it and restarts the server. Only a server whose root is `<data>/app/node_modules/whose-turn` is offered an update; a checkout is not. Why: releases are frequent during the alpha, and a user should learn about one while working and take it with one click, while a new Claude session takes it on its own: the plugin's SessionStart hook reads `update` and calls `POST /api/update` (that part lives in BladeForge). Ten minutes, not an hour, because during the alpha a fix often follows a report within the hour; the ETag cache keeps the extra checks free. This is announced, expected behaviour (the chip, the notification, the session), not a silent update: nothing installs without the click or the session start. The session part is superseded by the RMA-329 amendment below.

**Amendment, 2026-11-04 (RMA-329).** A session start no longer installs an update: `POST /api/update` runs only on the window's Update button or when the user says yes to Claude, and the notification promises only the window. Why: the security audit of RMA-286 rated the silent install a major risk for a public plugin, because one bad npm publish would run on every machine at its next session start, and the maintainer chose consent over convenience.

**Amendment, 2026-11-04 (RMA-330).** A pinned install is never offered an update and refuses `POST /api/update` with `PINNED`. The server reads the pin itself, from the exact version recorded under `dependencies` in `<data>/app/package.json` first (npm writes one for `--save-exact`; a plain install records `^x.y.z`, which is not a pin), and falls back to `WHOSE_TURN_APP_VERSION` in the server's own environment when the record holds none. `update.pinned` carries the version and `available` is false. Why: the plugin hook hid the offer while the variable was set, but the window button and the MCP tool installed `latest` over the pin anyway; the plugin's own check can go once its install passes `--save-exact` for a pin.

**Amendment, 2026-11-04 (RMA-328).** A release is refused until the BladeForge skill knows its version. The skill sync writes the monitor version it covers into `plugins/whose-turn/monitor-version` in BladeForge. `scripts/skill-knows-release.mjs` reads that file from BladeForge `main` through `gh api` and exits 1 unless it equals the `package.json` version, also when the file is missing or the call fails. The pre-push hook runs it on a push to `release`; `release.yml` runs it before `npm ci`, with the workflow's `GITHUB_TOKEN`, so a push that skipped the hook still fails before publish. Why: the order in AGENTS.md (RMA-325) lived only in prose and 1.0.0-alpha.9 shipped ahead of its skill sync.

**Amendment, 2026-11-05 (RMA-341).** After a successful monitor install the updater also updates the Claude plugin: it runs the Claude CLI's own `claude plugin update whose-turn@bladeforge` and nothing else, found on `PATH` or in `~/.claude/local`, `~/.local/bin`, `/opt/homebrew/bin` and `/usr/local/bin`. Security: the arguments are fixed in `lib/update.mjs`, there is no shell and no user input reaches the command, the confirm-flag that accepts a changed marketplace command is never passed (a CLI that wants it counts as a failed update), the call has a 60 second limit, and it runs only inside `POST /api/update`, so only after the window's click or the user's yes to Claude (RMA-329 stands). The result is `update.plugin: {state, copy}`: `state` is `updated`, `manual` (no `claude` found) or `failed`, and `copy` is the text the chip copies, chosen on the server; it is kept in `update.json` for the version it was run for, so the restarted server still reports it. The step never fails the monitor update and `POST /api/update` keeps its contract. The open Claude session picks the updated plugin up when the user types `/reload-plugins --force` in it; nothing outside the session can trigger that, and it does not work over a remote connection ([Claude Code CLI reference](https://code.claude.com/docs/en/plugins/cli-reference), "/reload-plugins"). So the chip, its one place, says "Reload Claude skill · Copy" and copies `/reload-plugins --force`, or "Update Claude skill · Copy" with `claude plugin update whose-turn@bladeforge` when `claude` was not found or the update failed. A copy is reported with `POST /api/update/plugin-copied`, which marks the result copied in `update.json`: the chip is gone for that version in every window, and `update.plugin` is gone for Claude too. Why: the plugin updates apart from the monitor, and an old plugin keeps its old hook and skill and does not know the new tools. Knowing whether the plugin is behind needs the hook to report its version, a follow-up in BladeForge.

**Amendment, 2026-11-07 (RMA-416).** `findClaude` reads only the absolute entries of `PATH`; an empty or relative entry such as `.` or `bin` is skipped, so a `claude` in whatever directory the server runs from never runs. Every other location, `PATH` and the four install folders above, is trusted as the user's own shell trusts it when they type `claude`: a process able to plant a binary there already runs as the user. The same lookup serves the report composer in `lib/compose.mjs`.

**Amendment, 2026-11-07 (RMA-424).** The chip copies `/reload-plugins --force` in every state: `updated`, `manual`, `failed` and `behind`. The terminal command `claude plugin update whose-turn@bladeforge` is no longer offered, because pasted into Claude it does nothing by itself, and after a monitor update the plugin on disk is usually current already: what is left is the reload in each open session. `manual` and `failed` keep the error colour, and their hint says to ask Claude to update the plugin if the reload changes nothing.

## Consequences

Easier: one command installs server, window and skill on a clean machine; a version bump is one tag. Harder: a release needs the package's trusted publisher on npm to name this repository and `release.yml` (OIDC, so no token lives in the repository; RMA-235) and a version bump in `package.json` before the tag (the workflow refuses a mismatch; until RMA-217 also in `.claude-plugin/plugin.json`); during the alpha the BladeForge entry follows the `alpha` dist-tag, so every alpha publish reaches users on their next plugin update. Impossible: a user building the window on their machine.
